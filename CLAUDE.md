# ColdChainSG

Course prototype (DBA5102 Blockchain): tracks chilled shipments through Singapore's cold chain and issues tamper-evident quality certificates. A neutral evidence layer, not a payment system.

## Inputs

- `docs/brief.md`: the original build brief.
- `docs/decisions.md`: binding design decisions (#1–36). Where they differ from the brief, the decisions win.
- `data/raw/*.csv`: the demo sensor logs (compliant, breached, tampered). They're generated by `data/generate.ts` with a fixed seed, so their SHA-256 hashes never change. Don't hand-edit them.

## Outputs

- `contracts/`: four Solidity contracts (ParticipantRegistry, ShipmentCustody, SensorOracle, CertificateRegistry). Hardhat 3, OpenZeppelin.
- `services/`: identity, custody, oracle and certificate services (Express + TypeScript), plus `common/` for shared env, db, chain, auth and test helpers. Each service keeps its tables in its own Postgres schema.
- `frontend/`: React + Vite + Tailwind. Users sign custody, resolution and decision transactions in MetaMask.
- The demo: `docs/demo-script.md` and `npm run seed`.

## Checks

- Work is done when `npm run test:all` passes. It runs the browser, contract and service suites on an isolated stack (chain :8546, services :4101–4104, web :5174), so it never touches the demo. It needs Postgres on :5433.
- A new contract rule gets its test first, in `contracts/test/`, and you watch it fail before implementing.
- Any `.sol` change follows the `contract-change` skill (test first, Slither via `npm run slither`, ABI consumers, decision row).
- `npm run test:contracts` is the quick in-process check while iterating on Solidity.

## Constraints

- No payment, escrow, bond or token-transfer logic anywhere, even if it's easy to add.
- The decisions in `docs/decisions.md` are binding. To change one, propose it, get agreement, then record it there.
- Raw sensor data, readings and notes stay off-chain. Only hashes, summaries and signed checks go on-chain.
- Never read `.env`; use `.env.example` for its shape.
- Ask before deploying to Sepolia or running `git push`.
- Step-by-step procedures (running the demo, redeploying, onboarding) belong in skills, not in this file.
